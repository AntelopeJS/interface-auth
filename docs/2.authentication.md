Authentication establishes trust in a token. Authorization decides what its holder may do. This interface connects token verification to API parameter injection. Your application supplies credential checks, payload validation, and access rules.

## Authentication flow

An authentication flow has four steps:

1. Token generation. `SignRaw` or `SignServerResponse` signs user data into a token.
2. Token transport. The client sends the token in the chosen header or cookie. You choose the client's storage and CSRF protection. This interface configures neither.
3. Token validation. The server verifies the token on each request.
4. Authorization. Your code checks whether the authenticated user may access the requested resource.

### Example authentication flow

The persistence functions in this example, `validateUserCredentials` and `getUserProfile`, belong to your application. The profile route verifies a token. A validator would add the payload shape and resource permissions. For production cookies, you also decide the Secure, SameSite, expiry, and CSRF policy of your deployment.

```typescript fragment
import { SignRaw, Authentication } from "@antelopejs/interface-auth";
import {
  Controller,
  Post,
  Get,
  JSONBody,
  HTTPResult,
} from "@antelopejs/interface-api";

class UserController extends Controller("/users") {
  @Post("login")
  async login(@JSONBody() credentials: { email: string; password: string }) {
    // Validate credentials against your data store
    const user = await validateUserCredentials(credentials);

    // Step 1: Generate a token
    const token = await SignRaw(
      { userId: user.id, role: user.role },
      { expiresIn: "1h" },
    );

    // Step 2: Return token to the client
    const result = new HTTPResult(200, {
      success: true,
      user: { id: user.id, role: user.role },
    });

    result.addHeader(
      "Set-Cookie",
      `ANTELOPEJS_AUTH=${token}; HttpOnly; Secure; SameSite=Lax; Path=/`,
    );

    return result;
  }

  @Get("profile")
  async getProfile(
    @Authentication() userData: { userId: number; role: string },
  ) {
    // Step 3: the token is verified. Resource authorization is application policy.
    // An invalid token rejects the request before this code runs.
    return { user: await getUserProfile(userData.userId) };
  }
}
```

This cookie example requires HTTPS. `SameSite=Lax` is a starting policy for same-site browser use. It does not replace a decision on CSRF protection or cross-site requirements. The helpers named above are application code, not a complete login implementation.

## Authentication sources

An `AuthSource` function extracts the authentication token from the incoming HTTP request. The default source checks two locations in order:

1. The `x-antelopejs-auth` header.
2. The `ANTELOPEJS_AUTH` cookie.

The header contains the raw token, not `Bearer <token>`. A present header takes precedence even when it is empty or invalid. Authentication does not retry with the cookie after verification fails. The default source does not read `Authorization`.

### Create a custom source

Implement the `AuthSource` type to extract tokens from a different location.

```ts docs-check
import { CreateAuthDecorator, AuthSource } from "@antelopejs/interface-auth";
import type { IncomingMessage } from "node:http";

const bearerTokenSource: AuthSource = (req: IncomingMessage) => {
  const header = req.headers.authorization;
  if (header?.startsWith("Bearer ")) {
    return header.slice(7);
  }
  return undefined;
};

const BearerAuth = CreateAuthDecorator({
  source: bearerTokenSource,
});
```

The `AuthSource` type signature is:

```typescript
import type { IncomingMessage, ServerResponse } from "node:http";

type AuthSource = (
  req: IncomingMessage,
  res: ServerResponse,
) => string | undefined;
```

## Authentication verifiers

An `AuthVerifier` function validates the token and extracts its payload. The default verifier is `ValidateRaw`, which calls the module that implements this interface, such as `@antelopejs/auth-jwt` for JSON Web Tokens.

### Create a custom verifier

```ts docs-check
import {
  CreateAuthDecorator,
  AuthVerifier,
  ValidateRaw,
} from "@antelopejs/interface-auth";

const userVerifier: AuthVerifier<{ userId: string }> = async (
  data,
  options,
) => {
  const payload = await ValidateRaw(data, options);
  if (typeof payload === "string" || typeof payload.userId !== "string") {
    throw new Error("Invalid user payload");
  }
  return { userId: payload.userId };
};

const UserAuth = CreateAuthDecorator({
  authenticator: userVerifier,
});
```

A verifier must establish trust in the token before it returns the payload. Decoding Base64 or parsing JSON alone does not authenticate a request. `ValidateRaw` returns an `AuthClaims`, which is `string | JsonObject`. The interface does not know the shape of what you signed, so reading a field needs a check like the one above. A configured validator receives the verifier's return type as its input.

The `AuthVerifier` type signature is:

```typescript
import type { AuthClaims, VerifyOptions } from "@antelopejs/interface-auth";

type AuthVerifier<T = AuthClaims> = (
  data?: string,
  options?: VerifyOptions,
) => Promise<T> | T;
```

## Authentication validators

An `AuthValidator` function runs extra checks on the verified data. Validators run after the verifier. A validator can transform the result, or throw an error to reject the request.

```typescript
import { CreateAuthDecorator, AuthValidator } from "@antelopejs/interface-auth";

const adminValidator: AuthValidator = (claims) => {
  if (typeof claims === "string" || claims.role !== "admin") {
    throw new Error("Admin access required");
  }
  return claims;
};

const AdminOnly = CreateAuthDecorator({
  validator: adminValidator,
});
```

The `AuthValidator` type signature is:

```typescript
import type { AuthClaims } from "@antelopejs/interface-auth";

type AuthValidator<T = AuthClaims, R = unknown> = (data: T) => Promise<R> | R;
```

Without an `authenticator`, a validator receives the `AuthClaims` the default verifier returns. When you also configure an `authenticator`, the validator receives whatever that authenticator returns, so a typed verifier such as `userVerifier` above gives the validator a typed value.

## Authentication pipeline

The pipeline takes the request through three stages:

![The source extracts a token, the authenticator verifies it, and an optional validator enforces policy before injection. A thrown error stops injection.](./assets/authentication-pipeline.svg "illustration"){width="480"}

An omitted `source` or `authenticator` callback uses the default. There is no default policy validator. Without one, the decorator injects the verified payload unchanged.

| Stage           | Input                          | Output               | Failure boundary                                               |
| --------------- | ------------------------------ | -------------------- | -------------------------------------------------------------- |
| `source`        | Request and response           | Token or `undefined` | Missing input still reaches the authenticator.                 |
| `authenticator` | Token and verification options | Verified payload     | A thrown error or rejected promise stops processing.           |
| `validator`     | Verified payload               | Value to inject      | Throw to deny access. A falsy return value is not a rejection. |

A validator passed to a decorator call replaces the configured validator. It does not run after it as an extra check. To compose validators, keep the shared policy in a function that each validator calls.
