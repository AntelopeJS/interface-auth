## Overview

Use `@antelopejs/interface-auth` to sign tokens and inject verified payloads into API handlers. Your application still owns credential checks, payload validation, and permission rules. A valid signature alone does not grant access to a resource.

This interface depends on the [interface-api](https://github.com/AntelopeJS/interface-api) package, which provides the decorators that inject parameters.

## Core concepts

The interface has three layers:

- Token handling. `SignRaw`, `ValidateRaw`, and `SignServerResponse` sign and verify tokens.
- Authentication decorators. The `@Authentication` decorator and the `CreateAuthDecorator` function inject verified payloads into handler parameters.
- A pipeline you can change. Custom sources, verifiers, and validators replace each step of the flow.

## Installation

```bash
pnpm add @antelopejs/interface-auth
```

## Protect an endpoint

Start with a running AntelopeJS API module and an authentication module that implements this interface. Installing the package does not configure signing keys or attach a token implementation.

This controller requires a verified token for `GET /account`. It returns no claims, so you can check that your provider and transport work before you add payload validation.

```ts docs-check
import { Controller, Get } from "@antelopejs/interface-api";
import { Authentication } from "@antelopejs/interface-auth";

@Authentication()
class AccountController extends Controller("/account") {
  @Get("")
  status() {
    return { authenticated: true };
  }
}
```

Send an issued token in `x-antelopejs-auth` to receive `{ "authenticated": true }`. A missing or invalid token must fail verification before the handler runs. This route checks authentication only, not permission to read another user's account.

1. **Issue a token after you check the credentials.** Use [token handling](./3.token-handling.md) to choose `SignRaw` or `SignServerResponse` and set an expiry.
2. **Choose one transport.** The default source reads a raw token from `x-antelopejs-auth`, then tries `ANTELOPEJS_AUTH` only when the header is absent. For `Authorization: Bearer`, use the [custom source example](./2.authentication.md#create-a-custom-source).
3. **Require authentication.** Add [a parameter, property, or class decorator](./4.parameter-decoration.md) to the controller.
4. **Enforce your policy.** Validate the payload shape, and throw when the caller lacks permission. A validator that returns `false` injects `false`. It does not deny access.

## Choose where to customize

| You need to change         | Customize       | Keep this boundary                           |
| -------------------------- | --------------- | -------------------------------------------- |
| Where the token comes from | `source`        | Extraction does not establish trust.         |
| How the token is verified  | `authenticator` | Verify before you return a payload.          |
| Who may use the endpoint   | `validator`     | Throw to reject. Return the value to inject. |

Before you expose the route, test a missing token, an invalid token, and a valid token without the required permission, as well as the successful request. See [authentication and authorization](./2.authentication.md) for the complete pipeline.
