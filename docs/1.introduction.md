# Authenticate API requests

## Overview

Use `@antelopejs/interface-auth` to sign tokens and inject verified payloads into API handlers. Your application still owns credential checks, payload validation, and permission rules: a valid signature alone does not grant access to a resource.

This interface depends on the [Interface API](https://github.com/AntelopeJS/interface-api) package, which provides the decorator infrastructure for parameter injection.

## Core concepts

The authentication system is built around three main layers:

- **Token handling** - Sign and verify authentication tokens using `SignRaw`, `ValidateRaw`, and `SignServerResponse`.
- **Authentication decorators** - The `@Authentication` decorator and `CreateAuthDecorator` function inject verified user data into handler parameters.
- **Customizable pipeline** - Configure custom sources, verifiers, and validators to adapt the authentication flow.

## Installation

```bash
pnpm add @antelopejs/interface-auth
```

## Protect an endpoint

Start with a running AntelopeJS API module and an authentication provider bound to this interface. Installing the package does not configure signing keys or attach a token implementation.

1. **Issue a token after checking credentials.** Use [token handling](./3.token-handling.md) to choose `SignRaw` or `SignServerResponse` and set an expiry.
2. **Choose one transport.** The default source reads a raw token from `x-antelopejs-auth`, then tries `ANTELOPEJS_AUTH` only when the header is absent. For `Authorization: Bearer`, use the [custom source example](./2.authentication.md#create-a-custom-source).
3. **Require authentication.** Add [a parameter, property, or class decorator](./4.parameter-decoration.md) to the controller.
4. **Enforce your policy.** Validate the payload shape and throw when the caller lacks permission. A validator returning `false` injects `false`; it does not deny access.

## Choose where to customize

| You need to change…        | Customize       | Keep this boundary                           |
| -------------------------- | --------------- | -------------------------------------------- |
| Where the token comes from | `source`        | Extraction does not establish trust.         |
| How the token is verified  | `authenticator` | Verify before returning a payload.           |
| Who may use the endpoint   | `validator`     | Throw to reject; return the value to inject. |

Before exposing the route, check a missing token, an invalid token, and a valid token without the required permission—not only the successful request. See [authentication basics](./2.authentication.md) for the complete pipeline.
